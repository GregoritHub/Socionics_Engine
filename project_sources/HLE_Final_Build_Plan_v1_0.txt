0. What this document is
This is the work order for taking the HLE Full Crux engine from the state of the archive HLE_Full_Crux_C7_Source_v2 (milestone C7 held, progress 6 of 7) to a finished release. It is written for Astra, who receives it together with the source archive, the evidence archive, the companion paper HLE Final Build: Companion Theory, the Closure Ledger, and two probe files. Every term of theory used below is defined in the companion paper; section references of the form CT §n point there.
What finished means. Two releases, in order. Release 1.0 is milestone C7 complete: every requirement of Build Specification v10 §9 satisfied for all 32 route-and-polarity cells in both content settings, with the Model G and axis layers present as read-only structure. Release 1.1 adds the energy and conditioning extension as a declared engineering hypothesis behind a switch. Release 1.1 needs the author's ruling before it starts (Phase 7). If no ruling is on file, stop after Release 1.0.
How the batches are sized. [assumption] The author did not state Astra's capacity. Batches are sized from the record of earlier deliveries in the archive: the whole second setting (five modules, about 750 lines, plus tests and tools) was one delivery. Each batch here is smaller than that: at most three new or changed source modules, one test directory, one evaluation run and one short record. Each batch also names a split point, so a batch that proves too large can be stopped half-way without leaving the source in a broken state. If Astra's real capacity is different, merge or split along those points; do not reorder phases.
Two things are both called C7. In the archive, C1–C7 are the seven build milestones. In the author's corpus, C1–C46 is a register of open theoretical items. This document always writes milestone C7 or register C7. Astra never closes a register item; only the author does.
1. Standing rules
These hold in every batch. They restate the practice already visible in the archive's records; none is new.
The baseline kernel is sealed. Nothing under baseline/ is edited, moved or reformatted. hle_unified imports Model A from baseline/HLE_Rebuild_R21B/hle; new structure goes in new hle_unified modules. Inherited evidence archives are never rewritten.
Python 3 and the standard library only. No floats, weights, rates or randomness in engine code. Integers and exact structures only. Seeds appear only in evaluation fixtures.
Protocol before implementation. Each phase starts from a protocol file in contracts/ that states gates, panels, seeds, denominators and tolerances. It is hashed before the code it governs is written. Later amendments are separate files; the original stays.
Freeze before evaluation. An evaluation counts only if it ran on a recorded source freeze and every executed-file hash matches. A run that overlaps a source change is preserved and not counted.
Failures are kept. A failed test, a stalled run or a wrong expectation is recorded with its fix. Nothing failed or source-changed is relabelled a pass.
Independent audit. Auditors reconstruct claims from committed objects, events and access receipts. They do not import the participant selector, the executor or the scheduler they audit.
Controls must bite. A control removes the defining step at matched main cost against a fixed downstream question. It must change the downstream result and must be rejected by the ordinary auditor.
Labels create nothing. A type label, a route name or a record count never manufactures competence, knowledge, consent or authority. Abilities are established in fixtures or acquired through paid work.
Existing names keep their meaning. The native request called integrate realizes IT → I, which is Embody. The Crux route Integrate is ITS → ITS. No inherited API or record changes meaning.
Claims stay inside the declared domain. The workflow domain has at most eight tasks, eight inputs, two participants, unit-duration serial scheduling and local slots 0–1,000. Nothing proved there is reported as general.
Status tags. Every statement in a report carries one of: source_defined, derived, probe, bridge, interpretive, open, machine-checked. Machine-checked means checked on the R21B kernel; say so.
Stop and report to the author, without working around it, when: a gate fails twice after a correction; a change would touch baseline/ or alter an inherited contract; a ruling listed in section 10 is needed; or a result contradicts a statement in the companion paper. In the last case report the contradiction; do not tune toward the paper.
Every batch ends with a handoff record in docs/, named FB<batch>_Record.md: what changed, how, what becomes possible, commands run with counts, failures and fixes, the source-freeze identifier, and the next batch's entry state. The three questions are the specification's own standard (CT §9.3).

10. Phase 7 — Energy and conditioning extension, Release 1.1
Entry condition. A written ruling from the author that the extension is to be built (ruling R5 of the Closure Ledger). Without it, the build ends at 6.3.
What it is. Today every expenditure record in the engine spends the same amount of energy and of time, the raw auditor requires the two deltas to be equal, and route prices are 5 minus dimensionality. The theory (CT §6.5, §7.5, §8) says information and energy rank the eight positions differently on exactly one axis each way. The extension lets the wallet's two currencies diverge accordingly and adds a conditioning ledger as a view over history. It is an engineering hypothesis in the specification's sense. It is off by default and changes nothing in Release 1.0 behaviour when off.

Batch 7.2 — Two-ledger pricing behind a switch
Goal. Implement resource_model with values legacy-r4 (default) and grade-v1.
Read first. Energy_Contract_v1; model_g.py from batch 1.1.
Do.
The model is fixed when a world is created, stored in every checkpoint, and cannot change during a world's life.
Under grade-v1: the path, support seat and time charges of every Model A step are computed exactly as now; the energy charge of a step into a position is 4 minus that position's grade. Work that is not Model A processing charges energy equal to time, as now.
Version the auditors: for a legacy-r4 world the existing checks run byte-for-byte as before; for a grade-v1 world the auditor recomputes both charges independently from the type frame.
Tests: a legacy world is unchanged in every record; the two models give identical paths and time charges; energy charges equal the table of CT §8.2; exhaustion of either currency stops work with spending preserved; exact continuation under grade-v1.
Do not.
Do not change path selection. Do not edit baseline/. Do not change the default.
Exit gate.
All Release 1.0 methods pass with the default; new tests pass; a legacy world saved before this batch restores and audits identically.
If the batch is too large. Pricing and wallet first; auditor versioning second. Do not stop between them with the default path altered.
Batch 7.3 — The conditioning ledger
Goal. Make functional conditioning observable without giving it any force.
Read first. CT §7.3–7.5 and §8.3; axes.py from batch 1.2.
Do.
Add an auditor-side function that, from an actor's committed paid Model A steps alone, returns eight integer counts by element; from those, the four axis loads, the four axis tilts, and for each of D, C, N, H the integer sum over its three formula elements.
Report ties as ties. Report the reading as 'the cell with the greatest load', never as the actor's subtype.
Tests: the counts are reproduced from raw records without calling the engine; two histories that differ in one step differ in exactly one count.
Do not.
The ledger stores nothing in the world and feeds nothing back: no price, selection or Shell rule may read it. Any such use is a new contract and needs a new ruling.
Exit gate.
Ledger reproducible from raw records for every saved world of Phase 5; no engine record changed.
If the batch is too large. Counts first; loads, tilts and formula sums second.
