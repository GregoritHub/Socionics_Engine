# U1 migration contract

Version 1 · Applies to the unified-engine transition from the frozen R21B baseline.

This is an implementation contract. U1 establishes the baseline and reviewable requirements. It does not implement the common object runtime or validate the wider conception.

## Authority and compatibility

The target conception and the user's clarification govern the new architecture. Source-defined structures retain their original status. An engineering choice remains an engineering choice, and an open geometric or psychological interpretation remains open.

R21B's original protocol versions, allocations, failures, checkpoints, and test results retain their identity. Its reported release status is preserved. A new schema version or world contract cannot relabel a historical exhausted episode as successful.

There are two comparison modes:

| Mode | Required comparison |
| --- | --- |
| Representation migration | Under identical permitted commands and inputs, preserve material effects, observations and their delivery order, actor decisions, paid work, unfinished state, capacity provenance, and assessment results. A bijective ID adapter may normalize the encoding; it may not normalize away a meaningful difference. |
| New capability or revised policy | Preserve the baseline mode and its witnesses. Give the extension its own version, scope, and prospective acceptance cases. Behavioral differences require causal evidence and an explicit change record. |

Exact byte equality remains required within an unchanged checkpoint schema. Cross-schema migration uses a declared semantic projection and a lossless adapter, with exact reconstruction of the promised legacy information. A single favorable endpoint does not satisfy either comparison.

These are protection obligations and future conformance requirements. The evidence report identifies which ones are exercised by the current inherited suite. It does not claim that every new-domain form of every property has already been implemented.

## Minimum object interfaces for U2

The following are proposed contracts, not a requirement to force every object into one giant record.

| Concern | Minimum semantics |
| --- | --- |
| Instance address | Stable namespace/key identity, an exact revision, and an adapter for every legacy Ref. Value hashes identify shared structure only. |
| Definition | Immutable versioned form, constraints, source status, and reusable operation definitions. Unknown meaning is explicit. |
| Roles and capabilities | Validated role-specific state, with optional memory, agency, material interaction, and governance. Roles do not manufacture a complete mind. |
| Relation | Typed participants, direction, context, time/validity scope, provenance, and its own address when it changes independently or bears consequences. |
| Claim or occurrence | Referent and content plus explicit occurrence category; personal endorsement and assessor outcome remain separate fields or relations. |
| Composition | Constituent references, membership/boundary rules, ownership, and declared summary dependencies. Cyclic object references must remain finite identities. |
| Version history | Prior revision and causal basis; historical meaning remains reconstructible. Forward writes do not mutate prior revisions. |
| Compatibility view | A deterministic, lossless mapping to the legacy record within the declared scope; one authoritative writer for each migrated state. |

U2 must demonstrate two equal-looking distinct material instances; a material object with no cognitive capability; a relation with its own history; a false hypothesis with no fabricated world event; revision without altered past meaning; split/merge lineage; finite cyclic references; and a migrated legacy transaction/checkpoint that retains the protected projection.

U2 does not need to implement generalized Shell detection, fluent language, new institutions, or a numerical curvature law. Those have named later milestones.

## Operation and access boundaries

U2 must leave room for the U3–U4 interfaces: actor and context, input revisions, permitted evidence, operation definition, preconditions, required work, Model A route, partial progress, execution constraints, effects, and delivered consequences.

The world is authoritative about supported material transitions. A participant is authoritative about the existence of its own current account, not about the truth of that account. Evaluators can inspect declared evidence but cannot insert their conclusions into participant decisions.

An operation can make a material change before all observers receive it. The event, observation, interpretation, and conceptual revision share lineage but have separate identities and completion times. A failed or invalidated internal job cannot retroactively cancel an already committed physical event.

## Evaluation design

New_Engine_Acceptance_v1.json names the prospective cases and protected properties for U2–U14. They are specifications, not newly passing tests.

Development uses seeds 3101–3105. The unified held-out panel reserves seeds 50001–50010, with independently varied histories, observation assignments, target categories, demands, and resources. Legacy R21C seeds 2001–2010 remain a separate reserved panel. Merely changing a seed is insufficient generalization; selected object/relation combinations and composition patterns must also be withheld.

Every case reports established, failed, or unassessed. Paid work that stops before a required result counts as incomplete, not as an excluded participant. Positive and zero/insufficient-resource expectations are defined separately.

Behavioral comparisons control type, history, available observations, resources, partner behavior, and seed. Mechanism removals identify whether a difference arose from routing, memory, projection, learned capacity, or imposed scenario content. Personality labels cannot prescribe the expected dialogue.

General composition is evaluated within the constructors and budgets actually supplied. No finite panel establishes unlimited development or a universal Shell detector. The Canon's generator condition must be demonstrated for a claimed general closure theorem; otherwise only evaluated compositions are claimed.

## Efficiency contract

U1 measures the unchanged baseline before selecting numeric migration targets. Efficiency_Acceptance_v1.json freezes those targets before U2 implementation and before tuning any optimized candidate.

Compare existing behaviors against the frozen baseline on identical workloads. Compare new features against an unoptimized implementation of the same feature set. Re-run both sides on the same environment; today's absolute time is a descriptive observation, not a portable timing gate.

Measure machine costs independently from simulated energy and time. Include compressed checkpoint size, restoration, historical reconstruction, live allocation, active work, observer overhead, and queue state. Larger genuine consequences may require larger work. Savings must come from less redundant representation or execution while preserving the protected semantics.

## U2 handoff

The baseline is in baseline/HLE_Rebuild_R21B. Module_Migration_Map_v1.json accounts for all 98 runtime modules and inventories their classes and record fields. Existing scenario drivers remain compatibility witnesses. Assessment readers must preserve independent reconstruction as schema adapters are introduced.

Start U2 with a separate unified runtime namespace and exact adapters for the smallest object/transaction slice. Keep the unchanged baseline executable for matched comparisons. Complete the eight U2 conformance cases and applicable inherited checks before extending the object system's responsibilities.
