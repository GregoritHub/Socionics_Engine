# U9 architecture and scope

Version 1 · 21 September 2026

## Contract and boundaries

U9 extends `DevelopmentEngine` through `CompositionEngine`. It retains the U2–U8 object, access, material, accounting, Model A, memory and Shell implementations. `CompositionEngine.adopt` replays an existing U8 checkpoint into the new engine without conferring any new procedure or primitive acquisition. Existing U6–U8 entry points continue to work. The new constructive work is scheduled through explicit requests, as in earlier native milestones; this milestone does not replace every existing autonomy policy or make all U6 forecasts consume arbitrary generated programs.

The workshop's standing needs, material laws, initial resources and primitive practice opportunities are supplied. No complete maintenance or return procedure is supplied. Search, individual action selection, effect realization, practice qualification, discrepancy generation and feature selection are runtime operations. The harness schedules opportunities, delivers observations and selects fresh material test cases. It does not provide a sequence, a branch condition, or an evaluator answer to the constructor.

## Representation

The common store holds versioned demands, search frontiers, candidates, capacities, procedure runs and selected actions. Candidates and retained capacities have actual `Procedure` and `Concept` facets; their executable structured fields hold goals, guards, constructors and exact dependencies. The generic U2 Procedure executor marker is `u9.structured.v1`. Its empty legacy `steps` field is not a second program: the U9 interpreter owns the structured program field. Results do not acquire U4 material effects from the presence of a Procedure role.

| Constructor | Meaning |
| --- | --- |
| `act(name)` | One actor-acquired U4 affordance, with explicit material input slots. |
| `seq(children)` | Ordered children; a residual interpreter stack remains between observed steps. |
| `if(test, yes, no)` | A relation over current processed fields, evaluated when the interpreter reaches the condition. |
| `choice(children)` | Ordered alternatives over learned entry guards. Selecting a body does not grant rollback or retry after a material failure. |
| `call(ref)` | An exact retained subprocedure version owned by this actor in the acquired context. |

Tests support typed equality/inequality and integer ordering, with field/value or field/field operands. Slots and references provide contextual grounding; object labels and evaluator labels are excluded from search and feature induction. Two things with the same label remain different objects.

The atomic domain comprises acquired `use`, `care`, `repair` and `return` operations. Their read/write footprints are listed in `composition_language.SCHEMAS`; the prediction model implements the declared U4 preconditions and effects. Physical execution still goes through U4, including current custody, finite consumables, tool wear, reservations, exact revisions and an actual return obligation. No new material law is introduced.

## Paid constructive lifecycle

1. **Notice:** Compare a standing goal with processed scalar material and relational evidence. Retain an open demand only for an observed gap; a satisfied goal is explicitly satisfied.
2. **Search:** Enumerate from acquired operations and current retained capacities. Existing procedure calls precede primitive extensions. Multiple guarded capacities also supply an ordered alternative constructor. Search changes hypotheses and retained work; it cannot change material state.
3. **Instantiate:** Create a run for an owned candidate or applicable retained capacity. Validate its dependencies and acquired primitives, preserving the structured continuation.
4. **Select and enact:** Pay to reach the next action using currently processed fields. U4 separately pays and commits the actual material step. A selected step can be attempted only once.
5. **Observe:** Deliver and pay to read the resulting native observation, then pay to integrate it. A run advances only on its own fresh executed step; use counts come from distinct observed successful uses. Observations update exact material and relation revisions.
6. **Retain:** A hypothesis becomes a reusable capacity only after complete observed successful performance of its declared goal. Retention changes an actor's capability record, not the world history of past failures.

Each constructive request uses a lawful paid Model A/Fold route. Preparation units are the number of evidence fields plus current state fields plus the stored repertoire's syntax size, plus a finite work allowance. For search, the allowance is `limit × (field_count + fuel + primitive_count)`; other operations use `fuel`. `fuel = 4 × limit × depth`. Route charges are added separately. These are conservative engineering prices, not a measurement of host CPU instructions or a psychological energy model. Default limits are finite; further requests can use larger limits. There is no automatic resource regeneration or refund for cancelled or unsuccessful work.

Actual bounded enumeration happens only after its ticket has been paid. Partial paid jobs produce no candidate. Interpreter insufficiency leaves the previous authoritative residual stack intact and records an unsuccessful work attempt; it can be retried with a larger funded ticket.

## Search coverage and continuation

The search state stores its initial evidence snapshot, goal, exact acquired repertoire, visited states, candidate prefixes, the next option within each partially expanded node, and a deferred frontier. One ticket considers at most its declared number of options. Repeated tickets resume the same queue. Increasing depth reactivates deferred nodes rather than resetting or fabricating earlier work. Representation length is not fixed at the old search depth.

`ticket_exhausted` means that a funded ticket stopped with queued work. `evaluation_budget` means a candidate's interpretation requires a larger funded bound. `repertoire_exhausted_at_depth` means the current finite depth was enumerated and longer prefixes remain deferred. `repertoire_exhausted` concerns only the acquired operations and retained calls in the recorded repertoire and state domain. None of these statuses asserts that no solution exists in all possible repertoires. An uncompleted energy/time payment remains a partial job, outside this enumeration vocabulary.

The search prefers a retained procedure before constructing a replacement. Consequently it can reuse a successful routine that performs more physical work than the shortest primitive-only solution. No optimality or efficiency claim is made. A separately implemented small exhaustive reference checks the first three-step maintenance result.

## Generalization and revision

The first observed successful procedure is generalized under the observed initial target condition. This intentionally limited induction rule does not assert universal validity. Its operation definitions still have their own feasibility conditions. In the declared counterexample, a one-use tool is damaged by the use step, so the old care step is physically unavailable. The failed step and all earlier material changes remain recorded.

A failed execution produces a pending consequence demand. Only an observed counterexample with adequate relevant resources and permissions can also produce a failed-generalization demand. Cancelled work is interrupted; received shortages/permission limitations and unexplained execution failure remain separately named. They do not automatically establish a semantic counterexample.

The generalized-repair demand retains the original failed start state. Search constructs a new branch from it; the continuing consequence demand separately describes work still owed in the actual current state. This distinction avoids quietly resetting the failed material or losing already performed work.

A new branch must be physically tested successfully. Retention then selects a differing observed nonidentity feature, records a conditional separator, and preserves the previous successful body through an exact versioned call. The demonstration distinguishes `target.max_wear == 1`. A new version does not erase its predecessor. A caller cannot invoke a superseded capacity as a current top-level answer; an explicit immutable historical call within the revised procedure remains resolvable.

## Access, replay and audits

Primitive definitions must be processed and acquired through the actor's own U4 practice. A visible definition alone is insufficient. Contextual acquisition is retained: the transfer tests use fresh objects and resource combinations within the learned workshop context, not an automatically inherited skill in every location or for another actor.

Snapshot assembly uses the latest processed revisions. Hidden material changes do not alter a participant's constructive choice. Freshly processed changes invalidate a pending prepared input; costs remain charged. U4 validates physical revision dependencies at execution. Detailed simulator failure reasons are not exposed as participant facts. U9 generated records cannot be supplied through the public draft-import operation or disclosed as another actor's private capacity.

Complete checkpoints replay commands, paid work, the material journal, access receipts, current capacities, search queues and residual interpreter stacks. The independent U9 auditor reconstructs work payments, owned acquisition, program-to-step decomposition, observed run advancement, referenced material state, retention and counterexample lineage. The inherited raw material auditor independently checks actual effects and resource conservation. The auditor does not rerun the participant's entire search algorithm as an independent completeness proof; frontier/depth correctness has targeted behavioral tests. Complete replay separately verifies disclosure selectors, which are not all represented in the raw material transaction stream.

## Claim scope

The protocol is a declared finite development panel. Its transfer cases are withheld from the participant's acquisition and induction until first use, but are not U14 release holdouts. The source documents constrain identities, preserved evidence, costs, observation isolation and scoped return claims. Constructors, inference rules, prices, feature selection and the finite workshop model are engineering choices.

No unrestricted semantic learner, natural-language communicator, arbitrary collective institution, numerical proof of the proposed higher-dimensional theory, universal compositional closure, performance acceptance or R21C release certification is claimed. Python, finite machine resources and funded search bounds remain practical limits. U10–U14 carry the remaining transition work.
